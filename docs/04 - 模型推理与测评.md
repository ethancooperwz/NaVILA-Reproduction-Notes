# 模型推理与测评

本文记录公开权重 `a8cheng/navila-llama3-8b-8f` 在 Habitat 的 R2R-CE `val_unseen` 上的评测。执行前先完成[环境配置](02%20-%20环境配置.md)和[数据集准备](03%20-%20数据集准备.md)。评测不更新模型权重，也不训练机器人底层运动策略。

## 1. 流程与本地代码修改

```text
语言指令 + MP3D 场景
        ↓
Habitat 生成观察，提取当前和历史 RGB 帧
        ↓
NaVILA 基于指令和 8 帧图像生成语言动作
        ↓
解析距离/角度，转换成 Habitat 基本动作并依次执行
        ↓
STOP 或达到步数上限（当前为 500 步）
        ↓
记录该任务的 NE / OS / SR / SPL / nDTW 等指标
```

环境虽配置 RGB 和深度传感器，当前高层模型输入只使用 RGB。`using queue...` 表示正在执行一个语言动作拆分得到的基本动作队列，不代表完成了新的任务；完成一条导航任务才会增加一次 episode 进度。

需要区分官方实现与本地修改：

| 项目 | 本地行为 |
| --- | --- |
| 模型设备 | `navila_trainer.py` 调用加载器时指定 `device_map={"": "cuda:0"}`，避免自动 CPU 卸载与整体 `.cuda()` 移动冲突；单卡仍须有足够可用显存 |
| 进度保存 | 每条任务结束后，将累计指标写入各分片的 `.json.progress`，临时文件写完、flush/fsync 后替换进度文件 |
| 恢复 | 加载进度，检查 episode ID 属于当前分片，筛掉已完成任务，继续评测剩余任务 |
| 最终结果 | 分片正常结束后输出 `.json`；已有最终文件时跳过该分片 |

上述保存恢复逻辑是本地新增功能，不是未经修改的官方源码行为。原始实现只在分片全部结束后保存指标。重新克隆官方代码时，需要移植本地 `navila_trainer.py` 中的 `save_eval_progress`、进度加载/过滤、每条任务保存及进度计数修改，不能只添加一个函数调用。环境相关的 TensorFlow 可选导入补丁见环境文档。

## 2. 启动前检查

所有评测命令均从 `NaVILA/evaluation` 目录执行：

```bash
conda activate navila-eval
unset PYTHONPATH

export NAVILA_ROOT=/你的实际路径/NaVILA
export CKPT_PATH="$NAVILA_ROOT/checkpoints/navila-llama3-8b-8f"
cd "$NAVILA_ROOT/evaluation"

nvidia-smi
python run.py --help

python - <<'PY'
import os
from pathlib import Path
from vlnce_baselines.navila_trainer import save_eval_progress

assert callable(save_eval_progress), "本地进度保存函数未定义"
assert (Path(os.environ["CKPT_PATH"]) / "config.json").is_file()
assert Path("data/datasets/R2R_VLNCE_v1-3_preprocessed/val_unseen/val_unseen.json.gz").is_file()
assert Path("data/datasets/R2R_VLNCE_v1-3_preprocessed/val_unseen/val_unseen_gt.json.gz").is_file()
assert Path("data/scene_datasets/mp3d").is_dir()
print("启动文件与本地保存函数检查通过")
PY
```

完整任务、GT、模型分片和场景检查见数据集文档。若使用未经修改的官方源码，上面的保存函数导入会失败，需先完成本地恢复功能适配。

用 `nvidia-smi` 检查的是**可用显存**，不只是显卡总容量。本地曾因旧进程占用 GPU 1 约 16 GB 导致加载失败；释放占用后两张 3090 才能各自运行一份模型。仅凭型号不能保证其他机器或设置下不会 OOM。

## 3. 单卡快速试跑与全量评测

### 只试跑 5 条任务

以下命令在前台运行，便于观察启动、动作输出和保存结果。试跑使用独立输出目录，关闭视频，避免试跑最终文件导致正式评测误判为已完成：

```bash
CUDA_VISIBLE_DEVICES=0 python run.py \
  --exp-config vlnce_baselines/config/r2r_baselines/navila.yaml \
  --run-type eval \
  --num-chunks 1 \
  --chunk-idx 0 \
  EVAL_CKPT_PATH_DIR "$CKPT_PATH" \
  EVAL.EPISODE_COUNT 5 \
  RESULTS_DIR eval_out_smoke \
  VIDEO_OPTION '[]'
```

正常结束后应生成 `eval_out_smoke/navila-llama3-8b-8f/VLN-CE-v1/val_unseen/val_unseen_1-0.json`，包含 5 条任务指标。少量任务仅用于调试，不能与论文全量结果比较。

### 单卡全量

```bash
bash scripts/eval/r2r.sh "$CKPT_PATH" 1 0 "0"
```

最后的 `"0"` 是物理 GPU 编号，换成 `"1"` 即使用物理 GPU 1。脚本设置 `CUDA_VISIBLE_DEVICES` 后，每个 Python 进程内的 `cuda:0` 对应它被分配的那张物理卡。

这条命令会运行全部 1839 条任务，不是快速测试。默认启用视频。不要在同一卡上重复启动另一份评测。

## 4. 双卡全量评测

### 使用官方启动脚本，默认生成视频

```bash
mkdir -p logs

bash scripts/eval/r2r.sh "$CKPT_PATH" 2 0 "0,1" \
  2>&1 | tee "logs/r2r_dual_$(date +%Y%m%d_%H%M%S).log"
```

四个位置参数依次为 checkpoint、总分片数、起始分片编号和物理 GPU 列表。当前数据按连续分片分成 920 条与 919 条，两张卡分别运行 chunk 0、chunk 1。每张卡各加载一份完整模型，显存不会合并。这不是 `torchrun`，没有 `--nproc_per_node` 参数。

脚本内部使用 `&` 启动子进程再 `wait`；`Ctrl+C` 不一定结束这些 Python 进程。不要只根据启动脚本或 `tee` 的退出状态判断两份评测都成功。

### 双卡不生成视频，使用独立输出目录

若主要目的是复现指标，可直接调用相同评测入口并覆盖 `VIDEO_OPTION`。下面也为两张卡分别保存终端日志、Habitat 日志和 PID：

```bash
export EVAL_RESULTS_BASE=eval_out_novideo
export RUN_LOG_DIR="logs/r2r_novideo_$(date +%Y%m%d_%H%M%S)"
mkdir -p "$RUN_LOG_DIR"

for GPU_ID in 0 1; do
  CUDA_VISIBLE_DEVICES="$GPU_ID" PYTHONUNBUFFERED=1 python run.py \
    --exp-config vlnce_baselines/config/r2r_baselines/navila.yaml \
    --run-type eval \
    --num-chunks 2 \
    --chunk-idx "$GPU_ID" \
    EVAL_CKPT_PATH_DIR "$CKPT_PATH" \
    RESULTS_DIR "$EVAL_RESULTS_BASE" \
    VIDEO_OPTION '[]' \
    LOG_FILE "$RUN_LOG_DIR/habitat_${GPU_ID}.log" \
    > "$RUN_LOG_DIR/chunk_${GPU_ID}.log" 2>&1 &
  echo "$!" > "$RUN_LOG_DIR/chunk_${GPU_ID}.pid"
done

wait
```

两种双卡启动方式选一种，不要同时运行。无视频模式仍计算同一组导航指标，但不绘制并编码视频；能节省多少时间取决于推理与可视化各自的开销，不能保证固定加速倍数。上述命令使用新目录，不会接上 `eval_out` 中的旧进度。

当前参数只启动后台子进程，未使用 `nohup` 或终端会话管理器，不保证关闭终端后继续运行；评测期间保留启动终端。明天恢复时可重新执行同一组命令，日志使用新目录，评测结果根目录保持原值。

## 5. 输出位置、进度与耗时

默认输出目录为：

```text
eval_out/navila-llama3-8b-8f/VLN-CE-v1/val_unseen/
├── val_unseen_2-0.json.progress
├── val_unseen_2-1.json.progress
├── val_unseen_2-0.json
├── val_unseen_2-1.json
└── videos/
    └── episode=...-ckpt=0-spl=....mp4
```

- `.json.progress`：本地逐条保存的累计指标，是一个普通 JSON 字典，键为 episode ID，不是 JSON Lines。
- `.json`：对应分片结束后的最终指标字典。单卡全量文件名为 `val_unseen_1-0.json`。
- `videos/`：默认每条任务保存的视频；无视频模式不会新增任务视频。视频不包含恢复评测所需的完整指标。
- 默认运行日志在 `evaluation/train.log`；双卡共用此日志时内容会交错。上面的终端日志或分卡日志更便于定位报错。

使用 `eval_out_novideo` 时，将下面路径中的 `eval_out` 改为 `eval_out_novideo`：

```bash
export RESULT_DIR="$NAVILA_ROOT/evaluation/eval_out/navila-llama3-8b-8f/VLN-CE-v1/val_unseen"

nvidia-smi
pgrep -af 'python.*run.py.*navila.yaml'
```

统计每个双卡分片已保存的任务数：

```bash
python - <<'PY'
import json
import os
from pathlib import Path

root = Path(os.environ["RESULT_DIR"])
for chunk in range(2):
    final = root / f"val_unseen_2-{chunk}.json"
    progress = Path(str(final) + ".progress")
    path = final if final.exists() else progress
    if not path.exists():
        print(f"chunk {chunk}: 尚无已保存指标")
        continue
    try:
        stats = json.loads(path.read_text())
    except json.JSONDecodeError:
        print(f"chunk {chunk}: 文件暂不可解析，请停止评测后检查，勿直接删除")
        continue
    print(f"chunk {chunk}: {len(stats)} 条，文件：{path.name}")
PY
```

文件名中的 episode ID 不连续，不能用最大的 ID 当作已完成任务数。`.tmp` 是保存过程中的临时文件，不用它代替正式进度文件。

耗时应根据当前运行的已完成数量和时间估计。单卡可近似用“平均每条耗时 × 剩余任务数”；双卡看两个分片中剩余时间较长的一份。本地早期单卡 12 条任务平均约 26 秒，仅作历史参考，不能当作固定速度或保证双卡 6.5 小时结束。失败、长路径、视频开销及其他进程负载都会影响时间。

## 6. 安全停止、关机与恢复

### 停止

前台单进程先按 `Ctrl+C`。官方脚本或循环启动的后台 Python 可能继续运行，需要另开终端检查：

```bash
pgrep -af 'python.*run.py.*navila.yaml'
```

确认输出命令、checkpoint 和分片确实属于本次 NaVILA 评测后，向对应 PID 发送 TERM。以下 PID 仅是示例，必须替换为刚查到的实际 PID：

```bash
kill -TERM 12345 12346
```

等待几秒，重新用 `pgrep`、`nvidia-smi` 确认进程退出、显存释放。若确认同一进程仍不退出，再对该实际 PID 使用 `kill -KILL`。不要使用 `killall python`，也不要根据很久以前记录的 PID 直接结束进程。

TERM 不会替正在进行的任务额外保存状态，但本地实现已逐条保存先前完成任务；最后未提交到进度文件的任务会重跑。确认两个进程已退出，再正常关机。

### 恢复

明天重新激活环境、设置路径变量并进入 `evaluation`，然后执行与原来相同的启动方式。必须保持：

- 相同 checkpoint 内容与模型目录名、任务数据和评测设置；
- 相同总分片数、chunk 编号和结果根目录；
- `EVAL.SAVE_RESULTS=True`，保留 `.json.progress` 与最终 `.json`。

使用默认双卡视频命令启动的任务，恢复命令为：

```bash
conda activate navila-eval
unset PYTHONPATH
export NAVILA_ROOT=/你的实际路径/NaVILA
export CKPT_PATH="$NAVILA_ROOT/checkpoints/navila-llama3-8b-8f"
cd "$NAVILA_ROOT/evaluation"

bash scripts/eval/r2r.sh "$CKPT_PATH" 2 0 "0,1"
```

使用无视频启动方式时，应重新执行第 4 节的无视频命令，继续指向 `eval_out_novideo`。

启动后应出现“恢复评测：已完成……剩余……”；已有最终 JSON 的分片会跳过。当前代码在检查进度前仍会加载模型，所以即使分片已完成，也可能先看到权重加载日志。恢复保留已完成任务的指标，不恢复正在执行任务的图像历史、动作队列或模型缓存。

第一次使用本地恢复功能时，先让各分片保存几条任务，停止后检查 JSON 可读取，再重启确认已完成计数恢复且剩余数量减少。仅有视频或函数导入成功，都不能代替这项实际恢复验证。

不要把双卡 `2` 改成单卡 `1` 来续跑。若暂时只用一张卡，可保持总分片数为 2，分两次执行原来的两个 chunk，例如在物理 GPU 0 上依次运行：

```bash
bash scripts/eval/r2r.sh "$CKPT_PATH" 2 0 "0"
bash scripts/eval/r2r.sh "$CKPT_PATH" 2 1 "0"
```

原有已完成指标仍可复用，但前提是其他进程没有同时评测同一个 chunk。若要更换权重或重新做独立实验，选择新结果目录；恢复当前实验时不要删除旧进度。最终 JSON 的存在会触发跳过，即使它来自少量任务试跑，所以试跑必须使用独立目录。

## 7. 检查完整性并汇总指标

两张卡退出不等于评测完成。先检查最终文件，而不是拿 `.progress` 冒充完整结果。确认第 5 节 `RESULT_DIR` 指向本次实际输出目录，在 `evaluation` 执行：

```bash
python - <<'PY'
import gzip
import json
import math
import os
from pathlib import Path

root = Path(os.environ["RESULT_DIR"])
with gzip.open("data/datasets/R2R_VLNCE_v1-3_preprocessed/val_unseen/val_unseen.json.gz", "rt") as f:
    episodes = json.load(f)["episodes"]
ids = [str(ep["episode_id"]) for ep in episodes]
assert len(ids) == len(set(ids)) == 1839, "任务数据数量或 ID 异常"

# 与当前数据集 get_chunk 的连续切分方式一致。
chunks = 2
size = math.ceil(len(ids) / chunks)
seen = set()
fields = ["distance_to_goal", "success", "spl", "ndtw", "path_length", "oracle_success", "steps_taken"]
for chunk in range(chunks):
    path = root / f"val_unseen_{chunks}-{chunk}.json"
    stats = json.loads(path.read_text())
    expected = set(ids[chunk * size:(chunk + 1) * size])
    actual = set(stats)
    assert actual == expected, f"chunk {chunk}: 任务缺失、多余或分片不匹配"
    assert not (seen & actual), "分片间存在重复任务"
    seen.update(actual)
    for ep_id, metrics in stats.items():
        for field in fields:
            value = metrics[field]
            assert isinstance(value, (int, float)) and math.isfinite(value), (ep_id, field, value)
            assert value >= 0, (ep_id, field, value)
        for field in ("success", "oracle_success", "spl", "ndtw"):
            assert metrics[field] <= 1, (ep_id, field, metrics[field])
    print(f"chunk {chunk}: {len(stats)} 条完整有效结果")
assert seen == set(ids)
print("1839 条任务全部覆盖、无跨分片重复，核心指标有效")
PY
```

通过后运行官方汇总脚本：

```bash
python scripts/eval_jsons.py "$RESULT_DIR" 2
```

单卡全量时，将上述完整性检查的 `chunks = 2` 改为 `chunks = 1`，汇总命令最后的参数也改为 `1`。脚本会按所给分片数匹配文件；缺少文件时仍可能打印部分任务的均值，因此不能省略完整性检查。该脚本输出到终端，不会自动把汇总追加到某个 `result.json`。

| 汇总字段 | 指标 | 单位与比较方式 |
| --- | --- | --- |
| `mean_distance_to_goal` | NE | 米，越低越好 |
| `mean_oracle_success` | OS / OSR | 0～1，论文用百分数时乘 100 |
| `mean_success` | SR | 0～1，论文用百分数时乘 100 |
| `mean_spl` | SPL | 0～1，论文用百分数时乘 100 |
| `mean_ndtw` | nDTW | 0～1，论文用百分数时乘 100 |
| `mean_path_length` | 实际路径长度均值 | 米 |
| `mean_steps_taken` | 基本动作步数均值 | 以代码记录的环境步为准 |
| `total_episodes` | 汇总任务数 | 全量应为 1839 |
| `invalid_spls` / `invalid_distances` | 无效 SPL / NE 数量 | 应为 0 |

对比论文时，确认数据划分、权重、观察帧数、动作配置及指标单位一致。有限任务样本、部分分片结果或视频中的 SPL 标签均不能代替全量统计。进一步记录与对比见[实验结果与分析](06%20-%20实验结果与分析.md)。

## 8. 视频与失败案例分析

NaVILA 默认配置是 `VIDEO_OPTION: ["disk"]`，不是 StreamVLN 的 `--save_video` 参数。视频保存到本次结果目录的 `videos/`，带 RGB 画面、指令与俯视轨迹。`VIDEO_DIR` 在运行中按结果目录重设，不能只改默认配置中的旧路径来定位本次视频。

若只想观察少量案例，可使用第 3 节试跑命令，换一个新的 `RESULTS_DIR`，并把 `VIDEO_OPTION '[]'` 改为 `VIDEO_OPTION '["disk"]'`。当前入口没有通用的 `--episode_ids` 参数，不应直接照搬其他项目的选项。

- **成功**：执行 STOP 时位于目标成功半径内，`success=1`，当前阈值为 3 m。
- **从未到达目标附近**：`oracle_success=0`，结合指令和轨迹分析感知、理解或动作执行问题。
- **到过附近但最终失败**：`oracle_success=1`、`success=0`，可能是停止判断失败、离开目标或超时，不能仅凭这两个数断定唯一原因。
- **成功但 SPL 低**：实际路线较长，可能绕路、反复转向或回退。

分析时同时记录 episode ID、指令、动作文本、最终距离、路径和步数。进度在视频生成前保存，若保存后中断，可能存在该任务指标但没有对应视频；恢复会跳过已保存任务，所以视频数不一定等于结果数。
