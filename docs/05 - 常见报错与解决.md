# 常见报错与解决

本文以本地 NaVILA 环境及复现时实际遇到的问题为主。基础版本为 Python 3.10、PyTorch 2.3.0/cu121、Habitat-Sim/Lab 0.1.7、Transformers 4.37.2、DeepSpeed 0.9.5、FlashAttention 2.5.8。安装顺序见[环境配置](02%20-%20环境配置.md)，数据路径见[数据集准备](03%20-%20数据集准备.md)，启动及恢复见[模型推理与测评](04%20-%20模型推理与测评.md)。

## 1. 先区分警告和真正的错误

`Successfully installed ...` 表示相应安装已经完成，但仍需检查后面列出的依赖冲突；最后一行 Traceback 才是定位程序退出原因的重要线索。

| 提示 | 含义与处理 |
| --- | --- |
| `setup.py install is deprecated` | 旧项目安装方式的弃用提示，不等于编译失败 |
| `detached HEAD` | 检出指定 Git 标签后的正常状态，不影响安装 |
| `Setting ds_accelerator to cuda` | DeepSpeed 设备选择信息，不是报错 |
| Gym 停止维护的提示 | 不等于运行失败，不应为消除提示直接替换成 Gymnasium |
| pip 有新版本 | 不要求立即升级，本环境保留指定的安装工具版本 |
| `Special tokens have been added...` | tokenizer 提示，不能仅凭此认定加载失败，也不能仅凭此认定模型已正确加载 |
| `Cannot copy out of meta tensor` | 真正的模型设备加载错误，见第 9 节 |
| `CUDA out of memory` | 真正的显存不足，见第 10 节 |

记录报错时保留完整命令、首次异常及末尾约 50～100 行日志。不要只截最后半行，尤其是 OOM 后面包含的显存和进程信息。

```bash
conda activate navila-eval
export NAVILA_ROOT=/你的实际路径/NaVILA
cd "$NAVILA_ROOT"

git rev-parse HEAD
python --version
python -m pip --version
python -m pip check
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
nvidia-smi
```

## 2. Conda 环境读到了 `~/.local` 中的包

**表现**：已经固定了版本，却又出现 NumPy 2.x、Hugging Face Hub 1.x、Pydantic 2.x 等冲突；安装日志出现 `/home/ethan/.local/lib/python3.10/site-packages`。

这是本次复现曾遇到的用户包覆盖问题，不要先逐个重装所有依赖。隔离用户包并清除当前终端继承的 Python 路径：

```bash
conda activate navila-eval
conda env config vars set PYTHONNOUSERSITE=1
conda deactivate
conda activate navila-eval
unset PYTHONPATH

python - <<'PY'
import site
import sys
from importlib.metadata import distribution

print("Python:", sys.executable)
print("用户包启用:", site.ENABLE_USER_SITE)
print("用户目录仍在搜索路径:", any("/.local/" in p for p in sys.path))
for name in ("numpy", "huggingface-hub", "pydantic", "fsspec", "httpx"):
    try:
        package = distribution(name)
        print(name, package.version, package.locate_file(""))
    except Exception as exc:
        print(name, exc)
PY
```

预期 Python 指向 `navila-eval/bin/python`，用户包启用和用户目录搜索检查均为 `False`，依赖位置位于该 Conda 环境。Conda 的 `overwriting variable ['PYTHONNOUSERSITE']` 只是接管变量的提示。确认隔离后，再处理环境内部仍存在的版本冲突。

## 3. `ModuleNotFoundError: torch`、`habitat` 或 `habitat_baselines`

先检查环境和安装位置：

```bash
which python
python -m pip --version
python -m pip show torch habitat habitat-sim
```

- **缺少 Torch**：确认已执行环境文档中的 PyTorch 安装命令，而不是只安装了 pip/setuptools。不要让后续命令自动装入最新 Torch。
- **缺少 Habitat-Lab 或 baselines**：确认源码目录为 `third_party/habitat-lab`、版本为 0.1.7，先完成旧依赖调整，再在该源码目录执行安装：

```bash
cd "$NAVILA_ROOT/third_party/habitat-lab"
python setup.py develop --all

cd /tmp
python -c "import habitat, habitat_sim, habitat_baselines; print('Habitat 导入通过')"
```

`cd /tmp` 只是为了从源码外检查导入，不会下载或重新安装 Habitat。不要套用新版 Habitat 拆分子目录的安装命令。editable install 后移动或删除源码也会导致导入失效。

## 4. `No module named habitat_extensions`、`vlnce_baselines` 或 `llava`

NaVILA 的评测入口在 `evaluation`，而 VILA 包从 NaVILA 根目录安装。先确认两层目录没有混淆：

```bash
cd "$NAVILA_ROOT/evaluation"
python run.py --help

python -m pip show vila
```

若 `llava` 尚未安装，按环境文档从 `$NAVILA_ROOT` 执行 `python -m pip install -e .`，并完成后续兼容版本调整。不要靠随意拼接全局 `PYTHONPATH` 掩盖环境或目录错误。

## 5. Habitat 编译停在 `Cloning into .../src/deps/eigen`

这是在下载 Git 子模块，不是已经进入 C++ 编译。Eigen 的地址可在 `.gitmodules` 中核对；本地版本使用 GitLab，pip 国内镜像不会加速这一步。

原命令长期无进度时，先停止它，再在 Habitat-Sim 源码目录单独显示子模块下载进度：

```bash
cd "$NAVILA_ROOT/third_party/habitat-sim"
git submodule update --init --progress src/deps/eigen
git submodule update --init --recursive --progress
```

下载成功后再运行 `python setup.py install --headless`。如果浏览器能访问而终端不能访问，检查终端是否使用了正确代理，不要假定代理软件已自动接管 Git。可做有限时连接检查：

```bash
curl -I --connect-timeout 10 --max-time 20 https://gitlab.com
```

保留仓库要求的子模块提交，不要随意换成最新 Eigen 或不明镜像版本。编译输出里的 warning 也不等于失败，应以最终退出状态和导入检查为准。

## 6. Habitat-Sim 补丁找不到文件

需要区分两种报错：

- **`can't open file .../habitat_sim_autofix.py`**：当前目录或 `NAVILA_ROOT` 不正确。
- **脚本输出 `habitat_sim/utils/common.py not found`**：尚未安装 Habitat-Sim，或安装布局不符合脚本搜索条件。该脚本只搜索 `site-packages/habitat_sim-0.1.7*.egg/...`。

先从 NaVILA 根目录执行：

```bash
cd "$NAVILA_ROOT"
ls evaluation/scripts/habitat_sim_autofix.py
python evaluation/scripts/habitat_sim_autofix.py
```

只有出现 `Replaced ...` 才表示成功。若仍找不到目标，在源码目录外检查实际安装位置：

```bash
cd /tmp
python -c "import importlib.util; print(importlib.util.find_spec('habitat_sim'))"
```

再根据实际位置检查，不要反复重编译或复制到猜测的 site-packages。补丁应在 Habitat-Sim 安装之后执行。

## 7. TensorFlow、WebDataset 等旧依赖冲突

### `No matching distribution found for tensorflow==1.13.1`

这是旧版 Habitat-Lab 依赖不支持 Python 3.10，不是清华镜像缺少文件。按环境文档第 4 节修改 baselines 依赖，删除 TensorFlow 1.13.1、改用指定 TensorBoard，并调整 MoviePy、WebDataset 后再安装。

### 评测时 `No module named tensorflow`

跳过安装 TensorFlow还不够：三个旧训练器原本在导入时强制加载它。按环境文档第 9 节应用可选导入补丁：

```text
evaluation/vlnce_baselines/common/base_il_trainer.py
evaluation/vlnce_baselines/dagger_trainer.py
evaluation/vlnce_baselines/recollect_trainer.py
```

本地这些文件没有直接使用 `tf`；兼容修改仅跳过 TensorFlow 本身缺失，不应屏蔽其他导入错误。不要为解决本地 PyTorch 评测导入而直接安装最新版 TensorFlow，避免改变已固定的 NumPy 等依赖。

### pip 报版本不兼容

先排除第 2 节的用户目录覆盖，再按下表处理：

| 冲突 | 本地兼容版本或处理 |
| --- | --- |
| Transformers 要求 `huggingface-hub<1.0`，却发现 1.x | `huggingface-hub==0.36.2` |
| 新版 Joblib 要求新版 Cloudpickle，而 Gym 0.17.3 要求旧版 | `joblib==1.3.2`，保留 Gym 的兼容依赖 |
| VILA 要求 WebDataset 0.2.86，但 Habitat 评测用 0.1.103 | 保留 `webdataset==0.1.103`，这是已知声明冲突 |
| 新版 W&B 反复回溯依赖 | 环境文档固定本地已安装的 `wandb==0.26.1`，避免无约束升级 |

上述冲突不能一概忽略。只将已说明的 WebDataset 声明冲突视作预期提示，其他问题应处理。重新安装 Transformers 或 DeepSpeed 后，要重新应用 NaVILA 的对应替换文件。

## 8. `nvcc` 不存在或 DeepSpeed 报 `CUDA_HOME does not exist`

PyTorch 的 CUDA 运行依赖不等于 CUDA 编译 Toolkit。DeepSpeed 0.9.5 即使设置 `DS_BUILD_OPS=0`，安装元数据阶段也会检查 Toolkit。

在评测环境内执行：

```bash
conda activate navila-eval
conda install -c nvidia cuda-toolkit=12.1 -y

export CUDA_HOME="$CONDA_PREFIX"
export PATH="$CUDA_HOME/bin:$PATH"
nvcc --version
python -c "from torch.utils.cpp_extension import CUDA_HOME; print(CUDA_HOME)"
```

预期 Toolkit 为 12.1、`CUDA_HOME` 指向当前环境，再按环境文档重试 DeepSpeed 安装。重新打开终端后，若要编译扩展，需要重新设置这些变量。不要仅凭 `nvidia-smi` 显示 CUDA 13.0 就认定已安装 Toolkit，或直接降级正常工作的显卡驱动。

## 9. `Cannot copy out of meta tensor; no data!`

本地曾在模型自动分配部分权重到 CPU 后，调用 `model.cuda()` 时触发该错误。`meta` 是加载/卸载机制中的占位张量，不能通过普通 `.cuda()` 从中复制实际权重；这不直接证明权重文件损坏。

对于一进程一卡的当前评测，可在 `evaluation/vlnce_baselines/navila_trainer.py` 中明确单卡加载：

```python
tokenizer, model, image_processor, context_len = load_pretrained_model(
    checkpoint_path,
    model_name,
    device_map={"": "cuda:0"},
)
```

不要再依赖一次整体 `model.cuda()` 来搬移自动分配、含卸载 hooks 的模型；明确单卡加载后，该整体移动语句可移除。每个进程的 `cuda:0` 对应启动器分配的物理 GPU。

此方式仍要求单卡有足够显存。如果接着报 OOM，按下一节检查占用。不要用 `to_empty()` 当作权重恢复办法；它本身不会加载缺少的参数数据。其他调用位置触发 meta 错误时，也需重新核对 traceback，不能全部归因于同一原因。

## 10. `CUDA out of memory` 与显存长期占用

先查看显存及占用进程：

```bash
nvidia-smi
nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_gpu_memory --format=csv
nvidia-smi --query-gpu=index,uuid,memory.used,memory.free --format=csv
pgrep -af 'python.*run.py.*navila.yaml'
```

- GPU 利用率为 0% 不代表没有显存占用，存活的进程仍可能持有模型权重。
- 本地曾有旧评测进程在 GPU 1 占用约 16 GB，使新评测加载失败；确认并停止旧进程后占用释放。
- 每张卡独立加载一份模型，两张 24 GB 不会自动成为一份 48 GB 显存。
- 本地正常评测曾使用约 21 GB 显存，但峰值随任务、缓存和配置变化，不能把它当作固定上限。

优先检查是否重复启动或有其他任务。对确认属于本次旧评测的实际 PID，按推理文档的停止步骤处理，不要结束不明进程。更换空闲卡时修改启动脚本最后的 GPU 列表，而不是盲目将所有代码里的 `cuda:0` 改为 `cuda:1`。

关闭视频可以减少可视化开销，但不是权重装不进显存的可靠解决办法。改变帧数、量化或模型切分属于额外实验设置，应单独记录，不能悄悄改完继续当作相同配置的论文复现。

如果仅在受限工具中出现 `Can't initialize NVML` 或查询不到驱动，回到实际运行评测的普通终端检查 `nvidia-smi`；不要仅凭工具环境中的查询失败就认定主机驱动损坏。

cd "$NAVILA_ROOT/evaluation"
readlink -f data/datasets/R2R_VLNCE_v1-3_preprocessed
readlink -f data/scene_datasets

当前默认路径分别为：

NaVILA/evaluation/data/datasets/R2R_VLNCE_v1-3_preprocessed/val_unseen/val_unseen.json.gz
NaVILA/evaluation/data/datasets/R2R_VLNCE_v1-3_preprocessed/val_unseen/val_unseen_gt.json.gz

## 12. `libGL.so.1`、EGL 或显示错误

这是渲染环境问题，和任务 JSON 是否齐全是不同层次。核对 Habitat-Sim 是否按 `--headless` 构建、宿主机 NVIDIA 驱动是否正常，以及环境文档中 OpenGL/EGL 系统依赖是否安装。容器还需确认图形设备和驱动库是否可访问。

```bash
nvidia-smi
ldconfig -p | grep -E 'libGL\.so|libEGL\.so'
```

动态库出现在列表中只是初步检查，不保证 EGL 一定能正常创建设备。保留具体 EGL 错误和仿真初始化日志再定位。`MAGNUM_LOG=quiet`、`HABITAT_SIM_LOG=quiet` 只减少输出，不修复问题；不要把安静日志当作成功，也不要随意设置虚假的 `DISPLAY`。

## 14. `NameError: save_eval_progress is not defined`

这是本地恢复功能移植不完整：已经添加保存调用，却没有定义保存函数，或缩进把函数放到了错误作用域。本地曾在第一条任务结束、首次保存时触发它；此前动作输出正常不代表保存功能可用。

在 `navila_trainer.py` 中，将 `def save_eval_progress(path, stats):` 放在模块顶层、类定义之前；不要插在 `@baseline_registry.register_trainer(...)` 与 `class NaVILATrainer` 之间。文件已有 `json`、`os` 导入，函数采用的实现如下：

```python
def save_eval_progress(path, stats):
    clean_stats = {
        str(ep_id): {
            key: value
            for key, value in metrics.items()
            if key != "top_down_map_vlnce"
        }
        for ep_id, metrics in stats.items()
    }
    tmp_path = path + ".tmp"
    with open(tmp_path, "w") as f:
        json.dump(clean_stats, f, indent=4)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp_path, path)
```

保存后先验证定义可导入：

```bash
cd "$NAVILA_ROOT/evaluation"
python -c "from vlnce_baselines.navila_trainer import save_eval_progress; print('保存函数已定义')"
```

这只检查函数存在。还需确认进度加载、已完成任务过滤及计数逻辑完整，再用少量任务做实际停止恢复验证，见推理文档。首次保存前报错的任务没有提交到进度文件，需要重跑。

## 15. `Ctrl+C` 不停、关机后不续跑或启动后直接跳过

### 后台评测进程仍在

官方 `r2r.sh` 内用 `&` 启动 Python，因此启动器被中断后子进程可能还在。先查出对应命令和 PID，再向确认过的进程发送 TERM；仍不退出时再考虑 KILL。不要使用 `killall python`。具体停止步骤见推理文档。

### 没有恢复进度

原版只在分片全部完成后保存；本地恢复依赖 `.json.progress`。检查当前结果根目录是否正确、进度文件能否解析，以及权重、任务、分片总数和编号是否保持一致。双卡从 `2` 改为 `1` 不会接上原来的分片文件。GPU 物理编号可变化，但 chunk 与结果的对应关系不能改变。

### 显示 `skipping -- completed evaluation exists`

当前代码只要发现对应最终 `.json` 就跳过该分片，不会先核对它是不是少量任务试跑的结果。试跑应使用 `eval_out_smoke`，正式评测使用独立目录。先检查最终文件的任务覆盖，再决定是否换新目录，不能一看到跳过就删除用于恢复的进度。

### 进度文件损坏或只有 `.tmp`

`.progress` 是普通 JSON 字典，不是 JSONL。先停止对应写入进程、备份文件并用 `python -m json.tool` 检查。不要跳过错误继续统计，也不要直接把 `.tmp` 或未完成的 `.progress` 改名成最终 JSON。原子替换可降低半写入风险，但不能保证任意磁盘故障下都可恢复。

已保存的任务会跳过，当前尚未保存的任务会重跑。只有视频不能恢复指标；本地进度保存发生在视频生成之前，所以可能存在指标已保存而视频未生成的任务。

## 16. 最终结果缺失、指标异常或脚本只汇总了一部分

NaVILA 最终结果按分片保存为 `val_unseen_2-0.json`、`val_unseen_2-1.json`，不是 StreamVLN 的 `result.json`，也不存在最后追加 `sucs_all` 的约定。

官方 `scripts/eval_jsons.py` 遇到缺少分片时仍可能输出已有任务的均值。必须先按推理文档检查每个分片的任务 ID、跨分片无重复、全部覆盖 1839 条任务且指标有效，再汇总。`Missing 2-1.json` 表示全量统计尚不完整，不是可以忽略的提示。

对比论文前核对：

- 权重是 `a8cheng/navila-llama3-8b-8f`，不是微调起始权重或其他模型；
- R2R `val_unseen` 全量完成，数据版本、GT 与任务匹配；
- 当前模型为 8 帧配置、基本动作前进 0.25 m、转向 15°，成功距离阈值为 3 m；
- 所有分片使用同一模型内容、精度及评测设置，未混用试跑结果；
- SR、OS、SPL、nDTW 原始值通常在 0～1，论文使用百分数时乘 100；NE 单位为米；
- 检查动作解析、超时、碰撞、停止判断等失败现象，不凭单个视频判断全量性能。

保留源码提交、环境版本、完整启动命令和分片最终 JSON。仍有问题时再查 [NaVILA 官方 Issues](https://github.com/AnjieCheng/NaVILA/issues)，不要套用 StreamVLN 的帧数、历史修复或 NCCL/torchrun 参数。

## 17. 视频无法生成或评测比预期慢

默认 `VIDEO_OPTION: ["disk"]` 会绘制俯视图、编码和写入任务视频，增加开销。关闭视频使用配置覆盖 `VIDEO_OPTION '[]'`，不是 `--save_video` 开关；双卡具体命令见推理文档。

若报 FFmpeg 相关错误，先检查可用编码器：

```bash
python -c "import imageio_ffmpeg; print(imageio_ffmpeg.get_ffmpeg_exe())"
ffmpeg -version
```

ImageIO 可能使用包内自带的 FFmpeg；系统 `ffmpeg` 命令缺失本身不能证明视频无法生成。只有确认系统可执行文件路径存在时，才设置 `IMAGEIO_FFMPEG_EXE`，不要无条件写死 `/usr/bin/ffmpeg`。

检查输出盘剩余空间和具体编码报错。若指标保存后视频生成失败，本地恢复会跳过该任务，缺失视频需另开独立可视化实验补做，不应删除指标来凑视频数量。

评测耗时取决于模型推理、每条任务长度、动作次数、可视化和机器负载。本地早期约 26 秒/条仅供参考，不保证固定完成时间。关闭视频不改变导航指标定义，但具体提速应实测；有进度时按剩余任务量估算，而不是按屏幕打印了多少行动作计算。
